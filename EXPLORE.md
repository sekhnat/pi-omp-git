# Exploration: pi-omp-git reference review

Reviewed `docs/pi-omp-git-reference.md` against upstream Pi at `a8ed497` and OMP at `b52e1f5` (both dated 2026-09-22). **The core approach is feasible**: Pi supports a `read` tool override, custom tools, slash commands, subprocesses, and custom TUI components. The following requirements need correction or clarification before implementation.

## Extension and workflow boundaries

1. **The promised PR workflow does not follow from `pr_checkout`.** In [§103](docs/pi-omp-git-reference.md#L3372), checkout returns a worktree path, but the example then calls `pr_push` and `run_watch` without changing context. Pi exposes the session cwd but [no supported extension API to switch that live cwd](https://github.com/badlogic/pi-mono/blob/a8ed497/packages/coding-agent/src/core/extensions/types.ts#L313-L393). Subsequent relative file tools and default branch/HEAD resolution still refer to the original checkout. The sequence is underspecified as written.

2. **The proposed package layout is not, by itself, a loadable Pi package.** [§5](docs/pi-omp-git-reference.md#L164) puts its entry point at `src/index.ts`; Pi discovers conventional `extensions/` entries or paths declared in the [`package.json` `pi.extensions` manifest](https://github.com/badlogic/pi-mono/blob/a8ed497/packages/coding-agent/docs/packages.md). The specification does not require that declaration.

3. **“Successful `bash` result” is not reliable GitHub-mutation evidence.** [§§57–58](docs/pi-omp-git-reference.md#L1958) require invalidation after shell `gh` mutations, based on successful Pi `bash` results. Pi’s [`tool_result` exposes an outer tool error flag, not the exit of each command in a shell expression](https://github.com/badlogic/pi-mono/blob/a8ed497/packages/coding-agent/src/core/extensions/types.ts#L1040-L1062); interactive `!` commands use a separate `user_bash` event, and external processes are unobservable. OMP’s own heuristic [invalidates **before** execution, including on command failure](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/tools/gh-cache-invalidation.ts#L1-L18). Guaranteed detection of *all* GitHub changes is impossible from this extension; the observable scope needs stating.

4. **OMP’s operation-specific approval is omitted.** OMP classifies GitHub reads versus mutations as [`read` or `exec` approvals](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/tools/gh.ts#L65-L151). Pi’s [registered-tool contract has no equivalent approval property](https://github.com/badlogic/pi-mono/blob/a8ed497/packages/coding-agent/src/core/extensions/types.ts#L453-L503). [§89](docs/pi-omp-git-reference.md#L2836) covers interactive discard intent but does not say what authorization, if any, is required for model-initiated PR creation, forced checkout, or push—particularly in non-TUI modes. OMP approval parity cannot be inherited automatically.

5. **The all-mutations lock guarantee is too absolute.** [§31](docs/pi-omp-git-reference.md#L1205) says all shared-repository Git mutations MUST be serialized and MUST NOT race, while only requiring cross-process locking as a SHOULD. An in-process mutex cannot serialize another Pi instance or an ordinary Git process. The guarantee and its stated mechanism conflict.

## Differences from current OMP, and internal contradictions

6. **`pr: 123` is not an accepted model-tool input.** [§24](docs/pi-omp-git-reference.md#L993) lists a numeric identifier, but [§18’s schema](docs/pi-omp-git-reference.md#L782) and [OMP’s actual schema](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/tools/gh.ts#L76-L101) accept a string or string array. Distinguish the PR number *as text* (`"123"`) from a JSON number.

7. **Existing checked-out branches behave differently in OMP.** [§28](docs/pi-omp-git-reference.md#L1123) requires a wrong-SHA `pr-N` branch to fail unless forced. [OMP checks that SHA only when no worktree already uses the branch](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/tools/gh-pr-checkout.ts#L439-L474); an existing worktree is reused. This is a stronger safety requirement than current OMP behavior, not exact parity.

8. **PR URL/repo conflict rejection is also stronger than current OMP.** [§50](docs/pi-omp-git-reference.md#L1765) requires an error on conflict. OMP’s checkout [passes the PR URL to `gh pr view`](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/tools/gh-pr-checkout.ts#L399-L415) and [`appendRepoFlag` silently omits `--repo` for URLs](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/tools/gh-common.ts#L44-L52). The safety improvement may be intentional, but it should not be described as matching OMP.

9. **“Immutable” means two different things.** [§9](docs/pi-omp-git-reference.md#L390) and [§7](docs/pi-omp-git-reference.md#L302) call PR resources immutable, yet [§§56–57](docs/pi-omp-git-reference.md#L1918) require refreshing and invalidating their content. In [OMP’s protocol contract](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/internal-urls/types.ts#L32-L38), `immutable` means **not editable by the agent**, not that future reads return identical bytes. The requirement currently conflates those meanings.

10. **Diff offsets mix bytes and string slicing.** [§15](docs/pi-omp-git-reference.md#L657) defines `startByte`/`endByte` but says to slice the `unifiedDiff` string with them. JavaScript string offsets are UTF-16 code-unit offsets; byte offsets will select the wrong section after non-ASCII text. [OMP in fact uses regex match indices and `string.slice()`](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/tools/gh-pr-diff.ts#L53-L77), despite calling them “byte” offsets in comments.

11. **The large-diff fallback has an unstated hard boundary.** [§17](docs/pi-omp-git-reference.md#L732) reads as though pagination can reconstruct any rejected aggregate diff. OMP [fails fallback when the PR exceeds GitHub’s 3,000-file per-file API limit](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/tools/gh-pr-diff.ts#L370-L386). The requirement and acceptance tests do not define that outcome.

12. **“Complete” failure logs conflict with the process cap.** [§44](docs/pi-omp-git-reference.md#L1607) requires complete logs to be persisted, while [§48](docs/pi-omp-git-reference.md#L1711) caps subprocess output at 8 MiB and only conditionally saves the complete content. OMP’s runner [discards bytes past 8 MiB](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/utils/github.ts#L21-L58), and its watcher calls that captured output a [full log](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/tools/gh-run-watch.ts#L644-L667). Complete-log parity is not assured by the specified runner.

13. **Dry-run is specified more strongly than OMP and inconsistently with optional staging.** [§74](docs/pi-omp-git-reference.md#L2399) permits staging all unstaged changes before proposal generation; [§104](docs/pi-omp-git-reference.md#L3413) calls dry-run “genuinely non-mutating.” Current OMP [stages all changes even when `dryRun` is true](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/commit/agentic/index.ts#L38-L49). The spec must distinguish its intended safer behavior from OMP parity and say whether dry-run may change the index.

## Contracts needing sharper boundaries

14. **Native `read` preservation needs more than `ReadToolDetails`.** [§7](docs/pi-omp-git-reference.md#L302) requires no filesystem-read regressions and native pagination, but the [Pi read tool also enforces byte/line truncation, continuation notices, out-of-range errors, and image handling](https://github.com/badlogic/pi-mono/blob/a8ed497/packages/coding-agent/src/core/tools/read.ts#L103-L183). It is unclear which of those apply to rendered URI content, especially across a cache refresh between paginated reads.

15. **Split-plan granularity does not match its correctness claims.** [§77’s proposal](docs/pi-omp-git-reference.md#L2510) identifies `files: string[]`, whereas [§§78–80](docs/pi-omp-git-reference.md#L2530) permit assigning different hunks of one file to different commits and conserving the original index and working tree. The plan does not identify those hunks. Hooks and concurrent external changes also make [§82’s “exact intended plan”](docs/pi-omp-git-reference.md#L2648) and unconditional conservation guarantees underspecified. [§100’s “two unrelated changes → split” test](docs/pi-omp-git-reference.md#L3185) additionally assumes a deterministic model decision.

16. **Partial batch checkout has no defined tool-level outcome.** [§24](docs/pi-omp-git-reference.md#L993) requires partial success but does not define whether the tool call succeeds, errors, or exposes a machine-readable partial status. Current OMP [returns a successful result containing both worktrees and failures](https://github.com/can1357/oh-my-pi/blob/b52e1f5/packages/coding-agent/src/tools/gh-pr-checkout.ts#L314-L352), which may be surprising to callers applying [§90’s error taxonomy](docs/pi-omp-git-reference.md#L2884).

No implementation or design changes were made.

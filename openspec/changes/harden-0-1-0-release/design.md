# Design

## Context

See `proposal.md` for motivation and the six delta specs for observable behavior. Source inspection: `src/shared/config.ts` documents project-over-user precedence but its pickers scan `[user, project]` and use first valid value; `src/index.ts` and `src/cli.ts` independently construct `~/.pi/agent`. The extension trusts project config after `session_start`; the standalone CLI always passes `projectTrusted: false`. `github.enabled` is parsed but not checked around the registered tool, virtual `read` override, prompt guidance, or shell observers. `src/git/commit-pipeline.ts` stages the full tree before agent planning when no changes are staged; dry-run uses a combined view. Extension commit parsing splits on whitespace and ignores unknown flags; CLI parsing is separate. The dispatcher is an 813-line combined schema/validator/switch while operation modules already exist. Git integration tests use real temporary repos, and GitHub tests use scripted seams. `package.json` declares only two of four directly imported Pi host packages as peers; Pi's package docs specify peer `"*"` for host packages and `getAgentDir()` is supported. The package version is currently `0.0.1`; no CI, license file, changelog, or security policy exists. README currently describes the unsafe behavior honestly. There are source references to `docs/pi-omp-git-reference.md` and ADR 0004 with no corresponding tracked docs in this checkout.

## Goals / Non-Goals

**Goals:** Keep one canonical config resolver and commit-option model, preserve the existing Git transaction and GitHub operation contracts, create testable seams for the feature gate/diagnostics, and validate the actual packed install before declaring 0.1.0 ready.

**Non-Goals:** No new GitHub operation, subprocess rewrite, generic service locator, change to Pi, or automated npm publishing credentials in this initial change.

## Decisions

### 1. One configuration service, host-supplied trust
Keep `loadConfig` as the sole field validator/resolver, with explicit highest-valid-layer selection in the correct order and the existing nonfatal invalid-file/value behavior documented. Pass the host's trust state, `getAgentDir()` result from `@earendil-works/pi-coding-agent`, cwd, and environment into this resolver; optionally return discovery/active-layer metadata for doctor. The CLI continues to treat project config as untrusted because it has no Pi trust signal; never infer trust from the existence of `.pi/pi-omp-git.json`. Audit all fallback paths in dispatcher, Actions watching, CLI TUI, cache, and nested operations and inject resolved paths instead of reconstructing `~/.pi/agent`. Preserve existing `PI_OMP_*` overrides and aliases. Alternative: duplicate Pi extension and CLI precedence logic; rejected because they would drift again. Do not introduce `commit.model` or `commit.autoStage` in this change: neither exists today and `--all` covers explicit intent.

### 2. Fail closed at each GitHub boundary
Use resolved `github.enabled` at the extension registration/advertisement boundary and again at execution time. Keep the `github` tool registration compatible with Pi's lifecycle; remove it from active/advertised tools when disabled where Pi permits, and provide a stable disabled error if an already-registered tool is invoked. Short-circuit virtual GitHub URIs before cache/availability probes, suppress prompt guidelines and shell `gh` invalidation when disabled, and leave non-GitHub `read` and `/git` untouched. Defer cache store construction as today. A CLI `--push` path that requires `gh` must return a disabled-specific result before `gh` execution; ordinary Git-only commits must still work. Re-evaluate at session/trust transitions and on each operation so config edits do not leave a stale enabled execution path. Alternative: only hide `github` in UI; rejected because virtual reads and observers can still execute.

### 3. Plan `--all` against a disposable index, commit against the real index only after validation
Change the pipeline's no-staged dirty path to a no-staged-changes result without invoking the agent or mutating state; preserve clean-tree `--push`. Explicit `--all` includes staged and unstaged changes. For planning and dry-run, start with a copy of the caller's index in a temporary location, stage all within that isolated index through a scoped Git runner using `GIT_INDEX_FILE`, and use that same view for status, diffs, file/hunk tools, and proposal validation. This includes untracked file contents in the preview instead of relying on the current `git diff HEAD` fallback, which omits their patches. On non-dry-run, after a valid proposal and any required confirmation, check that HEAD, caller's index, and relevant working-tree state still match the planned snapshot; then stage into the real index and verify its candidate tree matches the validated temporary tree before executing through the existing commit transaction and conservation checks. Abort on concurrent changes rather than silently widening scope. Always delete the disposable index and never copy it over the real one. A failed or absent proposal thus leaves the caller's index intact. Keep cancellation, bounds, argument-array execution, and changelog/commit verification; test partially staged files, untracked binary/rename/deletions, and conflict cases. Alternative: run `git add -A .` before planning and roll back on failure; rejected because restoring a possibly concurrent index is unsafe. A temporary working-tree clone would be heavier than a temporary index and alter Git semantics.

### 4. Shared parser, thin host adapters
Create a shared token-array commit parser with strict option/positional validation, `--` context delimiter, and explicit duplicate-context error. CLI parses `-C` separately and feeds only commit tokens to the shared parser; `/git` retains its existing revision parser. Pi receives a raw command argument string, so tokenize with a small quoted-string/escape-aware lexer before feeding the same parser rather than `split(/\s+/)`; use the host-provided structured tokens directly if that API is available. Keep model selection and UI/result rendering in their respective hosts. No implicit positional context before `--`; quoted CLI contexts are already a single argv token. Alternative: maintain separate parsers with mirrored tests; rejected because matching tests alone cannot enforce one contract.

### 5. Package and quality gates verify the install artifact
Declare the directly imported host runtime peers `@earendil-works/pi-coding-agent`, `@earendil-works/pi-agent-core`, `@earendil-works/pi-tui`, and `typebox` at Pi-recommended peer ranges; pin compatible versions in dev dependencies and update the lockfile, with no production duplicate of host packages. Add metadata, MIT license, security/changelog docs, and ensure the published `files` list contains actual runtime entrypoints and license/readme. `npm run check` runs typecheck, Biome check, and Vitest; CI calls it on Node 22 after `npm ci`, plus a small Linux/macOS matrix for Git-sensitive and packed checks where support permits. A dedicated `npm run smoke:pack` packs via `npm pack --json`, inspects the manifest/files, installs the tarball into a fresh temp directory with declared peers, verifies CLI `--help` and Pi extension loading using Pi's supported loader (not an incidental source-tree resolution), and cleans up. Make the smoke command avoid recursively calling `check`; CI runs check then smoke. Update test fixtures to use portable Git config isolation rather than `/dev/null` where needed. Alternative: only `node --import` from the source checkout; rejected because it misses missing files and undeclared peers. Use a documented manual release checklist with tag/version comparison, `npm run check`, `npm run smoke:pack`, tarball inspection, and deliberate `npm publish` with no stored credentials; do not create a publishing workflow until npm release ownership/trusted-publisher setup is confirmed.

### 6. Diagnostic model and incremental operation extraction
Create a host-independent doctor collector/formatter with injected probes for Git/gh versions/auth status, config metadata, path access, package version, and repository context. Prefer bounded subprocess calls with token-free summaries; do not print raw `gh auth status` output or process environment. Return classified records (OK, disabled, optional unavailable, actionable error); `/omp-git-doctor` and `pi-omp-git doctor` render the same data with host-specific presentation. Isolate probes so missing `gh`, cache permissions, or missing Pi runtime metadata do not crash the whole report. For dispatcher, retain the exported tool schema, operation identifiers, and public result/error contracts, but migrate one operation group at a time to registry entries with owned parameter fragments, validation, execution, and result mapping. Keep common runner, cache, availability, repository resolution, mutation lock, signal, and required path providers in a narrow typed operation context; avoid including UI unless needed. Extract pure ref/target decisions from PR checkout and Actions watching where useful, leaving actual Git/gh writes with their existing adapters. Differential tests compare representative old/new validation and results after each migration; no live GitHub access. Alternative: replace the dispatcher in a flag-day rewrite; rejected due to broad behavioral risk.

## Risks / Trade-offs

- [Temporary index does not capture a race in the working tree or some nonstandard index state] → Snapshot and compare index/tree/HEAD immediately before real staging, abort on mismatch, and cover split/partially staged cases with real Git repos; keep existing transaction checks.
- [Dynamically disabling Pi tools differs across TUI/print/session lifecycle] → Test Pi registration/active-tools behavior in a scripted host and enforce an execution-time guard regardless of visibility.
- [CLI cannot determine Pi project trust] → Continue user-only CLI configuration; expose this explicitly in doctor and documentation rather than accepting untrusted local files.
- [Node 22, SQLite, Pi's TypeScript loader, or macOS Git differs from the development host] → Exercise tarball in supported Node 22 CI; use a Pi loader fixture and portable Git test isolation; limit the initial matrix and document genuine platform constraints.
- [Monolithic dispatcher extraction alters obscure operation validation] → Preserve exported schema/input contracts, migrate incrementally with existing 1,320-line dispatcher test baseline and focused pure-function tests.
- [Manual release may be skipped] → Checklist names mandatory gates and requires recorded tarball/version review before publish; automate publication only after publisher ownership is established.

## Migration Plan

1. Pin down current behavior with regression tests, then land configuration/feature-gate and staged-only safety changes; document breaking effects and `--all` migration in README/changelog. Recheck observations against source at apply time if other work has landed.
2. Consolidate commit parsing, manifest and peers; install via `npm ci` and verify both host adapters.
3. Add `npm run check`, CI, and packed-fixture smoke before large architectural extraction.
4. Add shared doctor data and incrementally extract GitHub operation groups while continuously running existing tests.
5. Complete metadata/release docs, advance package version to 0.1.0 only when gates pass, verify tag/version and tarball, then follow the manual publication checklist. Rollback for pre-publication regressions is a code/config revert; once a version is published, fix forward with a new version, never overwrite npm's 0.1.0.
